## きっかけ

枠は `transform: scale()` で縮むのに、ブラウザ既定の 16px は追従しない。
スマホ幅では倍率が 0.373 しか無く、16px が 6px 相当になる（TODO-103 の
verifier が実測）。`docs/User.md` が「`px` や `rem` の直書きは崩れる」と
書いているとおりの状態で、本文の大きさを毎回書かないといけないこと自体が、
型からコピーしない人の負担になっていた。

TODO-103 で `docs/User.md` の「最小の例」を装飾なしの
`body: '<p>本文はここに書く</p>'` にしてあり、既定サイズを入れれば
そのまま読めるようになる。

## やったこと

`player.html` の `#slide-canvas` に既定の `font-size` を 1 つ足した。
変えたのはこの 8 行（コメント 4 行を含む）だけで、他のファイルは触っていない。

```css
#slide-canvas {
    font-size: clamp(1.0rem, 2.2cqw, 1.6rem);
}
```

`cqw` は枠 `.video-viewport`（`container-type: inline-size`）を基準に
解決されるので、枠の縮小に追従する。`font-size` を明示した要素は
そちらが勝つため、既存のスライドの本文には効かない。

値の決め方:

- `2.2cqw` — 既存スライドの本文で最も多いのは `2.0`〜`2.1cqw`。
  装飾なしの既定はそれよりわずかに大きくした
- 下限 `1.0rem` — 起点は `0.95rem` だったが、reviewer が
  「幅 768px・1024px の直後に下限が出て 15.2px になる」と実測したため
  `1.0rem` に上げた。既定サイズがどの幅でもブラウザ既定の 16px を
  下回らなくなる
- 上限 `1.6rem` — 擬似フルスクリーンで実際に効く値（reviewer が実測）

`docs/User.md` には「既定の大きさは本文向け」と TODO-103 で既に
書いてあったので、文書の変更は要らなかった。

## 確かめたこと

Playwright（chromium）でローカルサーバーに配信して実測した。
計測スクリプトと生データは `archives/agents/TODO-104/` にある。

**既存スライド 5 本（計 69 スライド）の見た目**（1280x800 と 390x844）。
`#slide-canvas` 配下の全要素の computed `font-size` を変更前後で突き合わせ、
325 要素で `16px` → `19.096px` / `20.02px` に変わった。内訳は
`DIV` 309・`A` 4・`LI` 3・`SPAN` 3・`IMG` 2・`UL`/`BLOCKQUOTE`/`ASIDE`/`FIGURE`
各 1 で、`<p>` は 0 件。`DIV` 以外の 16 件をソースで 1 つずつ確認したところ、
すべてテキストノードを直接持たない包みで、子はいずれも `font-size` を明示、
余白は `cqw` 指定だった。スクリーンショットの画素差分も、変更前どうしを
2 回読み込んで撮った差分（フォントの subpixel antialiasing 由来）と
同水準で、目視でも区別できなかった。

**装飾なしの `body`**（390x844、`docs/User.md`「最小の例」をそのまま使用）。
`<p>` の computed `font-size` が `16px` → `20.02px`、
`getBoundingClientRect()` の高さ（transform 適用後の実表示）が
`8.88px` → `11.09px` になった。

**下限が効く帯**（マウス想定、幅 760〜1300px を 59 点）。
最小値は 16px ちょうど（幅 768px・1024px）で、16px を下回った幅は 0 件。

## 分担の振り返り

**各担当が何を見つけたか。**
reviewer は、`clamp` の下限が幅 768px・1024px の直後に出て 15.2px になることを
実測で見つけた。main は「下限は狭い画面用の保険」としか見ておらず、
デスクトップの列構成の変化（Tailwind の `md`/`lg`）でコンテナ幅が
一段狭くなる帯があることに気づいていなかった。この 1 件で下限の値が変わった。
上限が擬似フルスクリーンで実際に効くことも、reviewer が測って示した。
verifier は、main の事前調査が取りこぼしていた要素を拾った。main は
`&slide=N` という URL パラメータでスライドを送れるつもりで走査していたが、
`player.html` にそんなパラメータは無く、実際には各デッキの 1 枚目しか
測れていなかった。verifier は `renderSlide()` を直接呼んで全 69 スライドを
走査し、変化した要素を 145 件ではなく 325 件と出した。

**見込みと食い違ったのはなぜか。**
担当の編成そのものは見込みどおり（reviewer + verifier、reviewer を先）で
食い違っていない。食い違ったのは main の事前調査の精度のほうで、
「実測した」つもりの走査が実は 1 枚目だけだった。

**次に同じ規模の項目をやるなら、どう組むか。**
同じでよい。CSS 1 行の項目でも、reviewer が値を 1 つ変えさせ、
verifier が main の計測の穴を塞いだので、どちらも省けなかった。
ただし main の側で 2 つ減らせた。1 つは、main が自前で走査を書いたこと。
同じ計測を verifier がやり直しているので、main は既存スライドへの影響を
「`<p>` に `font-size` があるか」の grep 程度で済ませ、実測は verifier に
一本化してよかった。もう 1 つは、main が走査の結果（「0 件」）を
確かめずに利用者へ報告したこと。スライドを送る手段が動いているかを
1 度確かめれば防げた。**自分で測った値を担当へ「実測済み、再測定は不要」と
渡すときは、測り方そのものが動いているかを先に確かめる。**
