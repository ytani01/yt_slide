## 分担の振り返り

**各担当が何を見つけたか。**

- **verifier（再現）** が、コードを読んだだけでは「進まないように見える」止まり
  だった疑いを、30 秒待っても進まないという実測に変えた。しかも
  「消音してから再生」は正常という対比まで出たので、直す場所が 1 か所に絞れた
- **reviewer** が、**読み終わりの待ち（1〜3 秒）の最中に消音したときも待ちが
  伸びる**ことを指摘した。main が「割り切り」として見込んでいたのは
  ナレーション途中の消音だけで、このケースは main も implementer も
  見落としていた。指摘を受けて分岐を 1 つ足し、待ちの最中は何もしない形にした
- **implementer** は項目 1〜6 を実装した。判断の要る箇所は無く、指示どおりに動いた
- **verifier（最終）** は 3 ケースの実測と文書 6 項目の突き合わせで、食い違い 0 件

**見込みと食い違ったのはなぜか。**

- 担当の組み方は見込みどおりだった。項目 7 で挙動が変わったので reviewer を
  入れる条件も、立てたときの想定のまま当てはまった
- 想定外は 2 つ。**implementer が API の利用上限で途中終了した**こと（同じ担当を
  再開でき、計測や調査を組み直さずに済んだ）と、**main が料金の 73% を
  占めた**こと
- main が重くなったのは、最初の突き合わせ調査で `player.html` 1631 行と
  文書 928 行を main が全部自分で読んだため。加えて、最後の見た目の確認で
  スクリーンショット 4 枚を main が自分で見た

**次に同じ規模の項目をやるなら。**

- **最初の突き合わせ調査を担当に回す。** ファイルを読んで「どことどこが
  食い違うか」を挙げるところまでを担当に任せ、main は挙がった食い違いの
  採否だけを判断する。ここが main の 73% の主因なので、いちばん効く。
  ただし規約に照らした確認なので `Explore` は使わない（`CLAUDE.md` を読まない）
- **スクリーンショットでの見た目の確認は verifier に渡す。** 今回 main が
  自分で 4 枚見たが、「枠からはみ出していないか」は判断の要らない確認で、
  画像のトークンを main に乗せる理由が無かった
- **コードを読んだ見立てがある項目は、今回と同じく実装の前に実測させる。**
  reviewer が別ケースを見つけられたのも、土台が実測で固まっていたから
