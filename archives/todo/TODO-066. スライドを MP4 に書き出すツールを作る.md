## きっかけ

URL を渡せない相手（メール添付、YouTube、オフラインの上映）にスライドを
届けたかった。`player.html` はブラウザと通信が要るので、そのままでは渡せない。

作るのは道具で、書き出した動画そのものは成果物ではない。

## やったこと

`tools/make-video.py` を足した。

    tools/make-video.py --slides readme          # video/readme.mp4 と video/readme.srt
    tools/make-video.py --slides readme --only 1 2   # 1 枚目と 2 枚目だけ

作り方は組み立てで、画面録画はしない。

1. Playwright（chromium）で `player.html` を 1 度だけ開き、`renderSlide(i)` を
   呼び直しながら各スライドを 1920×1080 の PNG にする。進行バー・ボタン・
   スライド番号は隠す
2. ナレーションに読みの置換表を当て、Google Translate TTS の mp3 を取る。
   180 字を超えるものは句読点の位置で分けて取り、連結する
3. `ffmpeg` の `atempo` で `BASE_SPEED_MULTIPLIER`（1.4 倍）に揃え、
   PNG と合わせて 1 枚ぶんのクリップにする。末尾に 2 秒の無音を足す
   （`player.html` の待ちの既定に合わせた）
4. クリップを連結して MP4（h264 / yuv420p / aac）にする
5. 字幕は `.srt` を別に出す。映像には焼き込まない

置換表の読み込みと読み上げ文の組み立ては `tools/measure-duration.py` と
丸ごと重なるので、**共通モジュールは作らず、`importlib` でそのまま読み込んで
使い回した**（`tools/test_measure_duration.py` と同じやり方）。
TTS の URL を組み立てる部分だけ `tts_url()` として切り出し、両方から呼ぶ。

書き出し先の `video/` は `.gitignore` に入れた。

## 確かめたこと

- **文書に書いたコマンドで `readme` 一式 10 枚を通しで書き出せる。** 1 分 31 秒。
  出来た MP4 は h264 / 1920×1080 / aac、120.1 秒
- **`.srt` の時刻と映像の実長のずれが溜まらない。** 最初は計算値で時刻を
  積み上げていて 1 枚あたり数十ミリ秒ずれていたので、実際に作ったクリップを
  測って積み上げる形に直した。差は 2 枚でも 10 枚でも 0.059 秒で、枚数に
  比例しない
- **180 字を超えるナレーションの分割も通る。** 現行の 4 本のスライド一式には
  180 字超が無くこの経路が一度も動かないので、一時的なスライド一式を作って
  215 字で通した。177 字 + 38 字の 2 つに分かれ、字幕も音声も欠けない
- **映像にスライド本体しか映っていない。** 書き出した MP4 からフレームを抜いて見た
- `tools/test_make_video.py` と `tools/test_measure_duration.py` が通る

### フェードの途中で撮っていた不具合

最初の版は**全スライドが半透明のまま焼き込まれていた**。`renderSlide()` が
0.35 秒の `fadeIn` を掛け直すのに、その途中で撮っていたため。
時間で待つのではなく、`renderSlide()` の直後に `slide-fade-enter` クラスを
外す形にした。

`ffprobe` の数値（長さ・解像度・音声の有無）はすべて正しく、**数値の確認では
最後まで出てこなかった**。見つかったのは、書き出した動画からフレームを抜いて
実際に目で見たとき。

## 分担の振り返り

**各担当が何を見つけたか。**

- **reviewer** — `.srt` の時刻を計算値で積み上げていて枚数に比例してずれが
  溜まる作り、180 字超の分割経路が現行のどのスライドでも一度も通らないこと、
  `CLAUDE.md` の「テストは 1 本だけ」が事実と食い違うこと、README と
  `docs/User.md` の文言の食い違い。**4 件とも main は気づいていなかった**
- **verifier** — 文書どおりのコマンドで通しで動くこと、`.srt` と映像のずれが
  枚数に比例しないこと、180 字超の経路が実際に通ること。いずれも
  reviewer の指摘に実測で決着を付けた
- **implementer** — 自分の検証を `ffprobe` の数値で済ませ、映像を見ていない
- **見つけられなかったもの** — フェードの途中で撮っている不具合。
  verifier は抜き出したフレームを見ていながら「フェードイン演出」として流した。
  **依頼文で「動画の画質・デザインの良し悪しは見なくてよい」と外したため**で、
  担当の落ち度ではなく依頼の切り方の問題。気づいたのは main が
  同じフレームを自分で見たとき

**見込みと食い違ったのはなぜか。** 担当の構成は見込みどおり。食い違ったのは
main の割合（料金の 69%）で、依頼文の作成と画像の確認を main が抱えたため。

**次に同じ規模の項目をやるなら。**

- **映像や画像を作る項目では、確認の依頼から「見た目は見なくてよい」を外す。**
  「デザインの良し悪しを評価しない」と「映っているものが正しいか見る」は別。
  フレームを抜いて**不透明か・欠けていないか・余計なものが映っていないか**を
  見るところまでを確認の担当の仕事にする
- **依頼文に実測したコード片を載せるときは、行を落とさない。** 今回の
  フェードの不具合は、実測時にあった待ちの行を依頼文から落としたのが原因
- **`ffprobe` の数値が揃っていることを「動いた」と読まない。** 出来たものを
  人の目で見る手順を、確認の依頼に必ず入れる
