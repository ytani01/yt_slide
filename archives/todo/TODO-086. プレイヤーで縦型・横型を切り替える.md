### 現状の確認

- `player.html` の `.video-viewport` とスマホ用 `#viewport-frame` は 16:9。
  擬似フルスクリーンの最大幅・最大高さも 16:9 を前提としている。
- 幅768px未満またはタッチ画面では、960×540 の内容を
  `setupViewportScale()` と `--vp-scale` で縮小する。
  `SLIDE_BASE_WIDTH_PX` と `SLIDE_ASPECT_RATIO` も横型固定。
- 字幕は枠外にあり、フルスクリーンでは枠の下へ配置する。
  音声エラー通知も画面の向きによる配置があるため、枠の変更と合わせて確認が必要。
- スライドには `body` と独自の `render()` があり、横並び・表・コードなどの
  配置は各スライドの HTML に含まれる。枠の比率変更だけで全配置が整うとは限らない。

### 実装案

- player の操作部に「横型 / 縦型」の選択を追加する。
  横型16:9・縦型9:16とし、初期値は従来どおり横型とする案。
  端末を回転する操作とは分け、PC・スマホのどちらでも手動で切り替えられるようにする。
- 向きに応じた比率と描画基準寸法をまとめて管理し、通常表示・スマホの縮小・
  擬似フルスクリーンのすべてに適用する。枠だけ縦長にして内容を引き伸ばさない。
- 縦型用のクラスまたは属性を設け、カードや比較欄を縦に積み、
  文字サイズ・改行・余白を縦型に合わせる。画面幅だけに依存した切り替えにしない。
  既存の `body` と `render()` を維持し、必要な配置指定をスライド側にも加える。
- 文字やナレーションを要約・省略せず、再生順序を保つ。
  切り替え時にもスライド番号、再生/一時停止、再生位置、字幕・音声の設定を保ち、
  読み上げの再開始や二重再生を起こさない。
- 独自 HTML を無条件に自動変換するのではなく、既存5種類のスライドで使う
  レイアウトを確認し、共通の指定と作者が調整する箇所を分けて文書化する。
  表・図・コードなど収まりにくいものは、実際の縦型表示を見て調整方法を決める。

### template の19種類から分かった懸念と対応案

記述に基づき、「懸念」は縦型に変更した場合の予測である。縦型表示の試作・
ブラウザ実測はまだ行っていない。対応案は実装時に検証する。

#### 共通の設計上の注意

- **向きの適用範囲を明示する。** player の選択状態を属性などで伝え、
  「縦型で積む比較欄」「縦型で縦につなぐ手順」など、対象の要素に明示した
  クラスへ適用する案。`.grid`・`.flex` 全体への上書きは、アイコンと文、
  Q&A、割合バーなどの必要な横並びまで変える。`md:` や物理画面の
  `orientation` だけでは、PC上の縦型表示を判定できない。
- **内側の描画寸法と文字の実表示サイズを一緒に決める。** 全19種類が
  `cqw` と `clamp()` を多用し、文字サイズはインライン指定も多い。
  仮に基準幅を960から540へ変えると、同じ `2cqw` は19.2pxから10.8pxになる
  （単位の計算例であり実測ではない）。`clamp()` の下限と外側の縮小も効くため、
  縦型に高さを足すだけで文字が読みやすくなるとは限らない。
  見出し・本文・注記・アイコンの共通サイズ指定を用意し、必要なインライン値も
  整理する案。`!important` の一括指定で独自の強弱を消さない。
- **見切れを隠さない。** player と複数の見本に `overflow-hidden` があり、
  はみ出しがスクロールとして現れず切れる可能性がある。余白と列数の調整を先に行い、
  全文を収める。収まらない場合に自動で小さくし続けたり、内容を落としたりしない。
  内部スクロールはスワイプのスライド送りとも干渉するため、試作で必要と判明した
  場合にだけ、具体例を示して採用と操作方法を利用者に確認する。
- **見た目と説明の意味を揃える。** 3の「2 カラム」、10の「半分の幅」「3 分の 1」、
  11の「横幅いっぱいの 1 行」、12の「横並び」、16の「左に本文、右に補足」は
  縦型と食い違う可能性がある。
  8の引用は16:9前提の文書を引用している。元が横型の型である注記を表示する案を
  第一候補にし、ラベル・ナレーション自体の変更が必要なら文案を実装前に確認する。
  11の帯を複数行にする場合もこの確認に含める。18で全面表示をやめる案を採るなら、
  見本の別バリエーションとして表示文・原稿の変更を確認する。
  引用は無断で書き換えず、参照先との一致を保つ。ナレーションを変更する場合に限り
  `duration` を測り直す。配置の切り替えだけでは原稿も読み上げ位置も変えない。
- **縦型の高さと字幕・操作部を両立する。** PCも含め、利用できる高さから
  ヘッダー・字幕・操作部の領域を考えて枠を収める。現行のタッチ画面向けの幅上限は
  枠の上端から画面下までで計算しているため、枠外字幕まで見えるとは限らない。
  端末の向きと選択した型の4通りで、字幕と通知が操作を隠さないか確認する。
  音声エラー通知は物理画面の `orientation` だけで位置を決めず、実際の空き領域を
  基準にする案。余白が足りなければ通知用の領域を確保して枠を調整し、通知の全文と
  再試行・音声エンジン切替の両ボタンが画面内で操作でき、本文・字幕・操作部を
  覆わない配置を試す。

#### template で先に検証する順序と合格条件

まず **10（spanと高さ）、12（線と対応関係）、5（長い文字列）、18（切り抜き）**
を試作し、共通指定で対応できる範囲を確かめる。その後、上表の残りを全件確認する。
優先順位は試作の順番であり、残りを省く意味ではない。

- 各枚のカード数、本文、コード、参照リンク、画像の説明、読む順番が横型と一致する。
  4の行見出しと値、6の接続順、12の段とファイル名、14の比率も保つ。
- 390×844に加え、特に小さくなりうる844×390の横持ち×縦型でも、
  フォント読込後の文字サイズと縮小率を記録し、同じ下限で判定する。本文・注記の
  許容する最小サイズは試作を見て利用者と決め、枠内に入っただけでは合格にしない。
  同じ下限と全文表示を両立できない組合せは、通常表示・フルスクリーンそれぞれの
  実測例を示し、表示領域やスクロールの扱いを実装確定前に相談する。
- 全19枚について、文字・カードの矩形と枠の内側、`scrollWidth/Height` と
  `clientWidth/Height` を確認し、クリップされていないか画像も見る。
  装飾の円・引用符と意図した画像の切り抜きは、本文のはみ出しと分けて判定する。
- 画像・Webフォントの読込完了後に確認し、引用リンクのクリック/Tab操作、
  図の矢印、接続線、暗幕と文字の視認性も確認する。縦→横へ戻して
  span・矢印・画像位置・文字サイズに縦型の指定が残らないことを確かめる。
