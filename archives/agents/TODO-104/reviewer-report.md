## 検討

### 1. デスクトップの 2 か所のブレークポイント（768px・1024px）で本文が下限（15.2px）まで落ちる

実測（`getComputedStyle(#slide-canvas).fontSize`、window 幅 700〜1280px、
高さ 900px、マウス想定）:

```
width  fontSize
767    20.02px   ← @media 側（幅 768 未満）の経路。960px 基準で常に一定
768    15.20px   ← 下限（clamp の 0.95rem）に張り付く
800    15.44px
900    17.64px
1000   19.84px
1023   20.35px
1024   15.20px   ← 下限に再び張り付く
1050   15.30px
1100   16.13px
1200   17.78px
1280   19.10px（以降 1920px まで頭打ち。main の `max-w-7xl` で
                video-viewport の幅が頭打ちになるため）
```

`main` の `grid-cols-1 lg:grid-cols-4`（`lg` は 768/1024 とは別に見えるが、
実際は Tailwind の `md`=768・`lg`=1024 の 2 段で列構成が変わる）が原因で、
768px と 1024px の直後に video 列の実幅が一段狭くなり、`2.2cqw` の値が
下限を割る。その後は同じレイアウト帯の中で幅が伸びるにつれ下限を離れて
20px 前後まで戻り、次のブレークポイントでまた下限に落ちる、という
鋸歯状の挙動になる。

**同じ現象は今回の変更より前から `#tap-feedback-icon`（60〜82px の帯で
同じ 768/1024 に落ち込む）で起きている。** 既存のコードベースの
`cqw` 指定の設計に元々ある性質で、今回の diff が新しく持ち込んだ不具合
ではない。ただし対象がタップ時だけ一瞬出るアイコンから、常時表示される
本文へ広がった点は、今回の diff で初めて生じる影響。

依頼にあった「マウスの PC でウィンドウを狭めた 768px 以上の帯」は、
実測するとこの 2 つの幅（768px と 1024px）の直後が該当する。狭い帯
（数十 px 程度）で、実害（読みにくいか）は主観の判断が要るため未確認。
15.2px は変更前（実測 6px 相当）よりは大きい。

### 2. `clamp` の上限（1.6rem = 25.6px）は擬似フルスクリーンで実際に効く

非フルスクリーンのデスクトップ表示では `main` の `max-w-7xl` により
`video-viewport` の幅が最大 918px 止まりで、上限（`1163.6px` 相当）には
届かない（1280〜1920px 幅で実測 19.10px 止まり）。

ただし `.video-viewport.pseudo-fullscreen`（擬似フルスクリーンボタン、
マウス PC でも使える経路）では `max-width: none` になり画面幅そのものに
広がる。実測では 1280x800・1920x1080・2560x1440 のいずれも
コンテナ幅が画面幅と一致し、`font-size` は 25.6px（上限）に張り付いた。
**上限は死んだ値ではなく、フルスクリーン時に日常的に効く。** 依頼文の
「実害が出る画面幅の帯」を上限側でも確認した結果として報告する
（実害の有無自体は未確認、25.6px は不自然に大きすぎる値ではないと見える）。

## 問題なしを確認した点（依頼の 1・3・4・5・6）

- **置き場所（1）**: `#slide-canvas` は `.video-viewport`（コンテナ）の
  子で、ヘッダーの `SLIDE nn / NN`（`text-sm`/`md:text-base` で独自指定）や
  `#tap-feedback-icon`（独自の `font-size`）を含まない、スライド本文の
  差し込み先だけに絞られている。`.video-viewport` 直下に置くより副作用の
  範囲が狭く、TODO チェックリストが求める「`li`・`div`・`span` への継承」
  にも `#slide-canvas` の方が届く（`.video-viewport p` では届かない）。
  妥当と判断。
- **コンテナの解決先（3）**: `player.html` 全体で `container-type` を
  持つのは `.video-viewport` の 1 か所のみ（`grep` で確認）。入れ子の
  コンテナは無く、`#tap-feedback-icon` など既存の無名 `cqw` 指定と
  同じコンテナに解決される。
- **詳細度・カスケード（4）**: `font-size` は継承プロパティなので、
  子要素に `font-size` を明示していなければ ID セレクタの詳細度に関係なく
  値が伝わる。既存スライド 5 本の `<p>` 55 個は全て `font-size` を
  インラインの `style` で明示しており（`grep` で `<p ... font-size` 以外の
  `<p>` が無いことを確認）、インライン style は ID セレクタより詳細度が
  高いので上書きされない（コメントの主張どおり）。アイコン
  （`<i class="fa-solid ...">`、141 個）も `template.js`・`claude-memo.js`
  で確認した範囲は全て、直近の親 `span`/`div` の `style="font-size: ..."`
  を継承しており、今回の変更の影響を受けない。
- **コメントの書式（5）**: インデント（8 スペース＋`/* `）、TODO 番号を
  文中に `（TODO-104）` の形で挟む書き方とも、直後の `#tap-feedback-icon`
  のコメントと一致。
- **docs との整合（6）**: `docs/User.md` の「### 文字の大きさを変えたく
  なったら」は「既定の大きさは本文向け」とすでに書かれており（TODO-103
  で先出しした記述、TODO.md の背景に経緯あり）、今回の CSS 追加でこの
  記述が実態と一致するようになった。矛盾は見つからず。`docs/User.md` の
  `#slide-canvas` に触れた別箇所（960x540 の説明）も今回の変更と無関係で
  食い違いは無い。`docs/Developer.md` の「副作用のある実装」節は音声周りの
  話で、この変更とは無関係。
